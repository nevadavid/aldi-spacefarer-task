# Galactic Spacefarer Adventure

SAP CAP application with a Fiori elements List Report and Object Page,
managing spacefarer candidates across the SAP galaxy.

## Running locally

```bash
npm install
cds watch
```

The app is served at http://localhost:4004.

Mocked users (Basic auth):

| User  | Password | Role       | Planet |
| ----- | -------- | ---------- | ------ |
| admin | admin    | Admin      | —      |
| terra | terra    | Spacefarer | EAR    |
| ares  | ares     | Spacefarer | MAR    |

`tests.http` contains ready-to-run requests for every scenario described below.

> Note: `@cds-models/` is generated by `cds-typer` and is git-ignored.
> Run `cds watch` once after cloning so the type definitions exist before
> the service starts.

## Database

Local development uses SQLite via `@cap-js/sqlite`, running in-memory. The
schema is deployed and the CSV seed data loaded on every `cds watch` start,
so each run begins from a known state.

For a persistent local database instead:

```bash
cds deploy --to sqlite:db/spacefarers.db
```

In production this would be SAP HANA Cloud. The CDS model is unchanged —
only the `cds.requires.db` configuration differs, which is the point of
modelling at the CDS level rather than writing SQL.

## Data model

Two kinds of entities, modelled deliberately differently:

**Code lists** (`Planets`, `Positions`, `Departments`, `SpacesuitColors`,
`WormholeNavigationSkills`) use `sap.common.CodeList`. They are configuration,
not data: the application does not work without them. `CodeList` gives value
help dialogs, human-readable text instead of keys, and localized labels for
free — none of which would work with UUID keys.

**`Spacefarers`** uses `cuid, managed`: it is transactional data with its own
lifecycle, created and edited through the UI, with audit fields populated by
the framework.

`WormholeNavigationSkills` deliberately uses an `Integer` key, because skill
levels form a natural rank — ordering and comparison follow from the model
rather than from code. The trade-off: the key is not human-readable in CSV
seed files, and inserting a level between two existing ones would require
renumbering. In a production system a `code: String(3)` plus an explicit
`level: Integer` would be more robust.

## Seed data

Code lists live in `db/data/` — they are deployed to every environment,
including production.

Spacefarer sample records live in `test/data/` — they are development and
test fixtures only. A production deploy must not create fictional people,
especially not ones the service would then email.

The rank thresholds (`requiredStardust`) are data, not code: changing the
progression is a CSV edit, not a redeploy.

## Service and authorization

CRUD is not hand-written. The CAP generic provider derives it from the CDS
model, and OData V4 supplies `$filter`, `$orderby`, `$top` and `$skip` —
which is why the List Report's sorting, filtering and pagination need no
application code. Custom code exists only where behaviour differs from the
generic case.

Authorization is declarative, in two layers:

- `@requires: 'authenticated-user'` on the service — no anonymous access.
- `@restrict` on the entity, with a `where` clause for row-level filtering:

```cds
{ grant: ['READ'], to: 'Spacefarer', where: 'originPlanet_code = $user.planet' }
```

CAP compiles this into the generated SQL `WHERE` clause. It is not a
post-query filter: a user from Planet X requesting a Planet Y record by its
direct ID receives **404, not 403** — the row does not exist from that
query's point of view, so the response leaks nothing about its existence.

Locally `$user.planet` comes from mocked users in `.cdsrc.json`. In
production the same model works unchanged against XSUAA with attribute-based
role assignment — only the auth provider changes.

## Custom event handlers

**`@Before` (`srv.before('SAVE', ...)`)** — validates and enhances the
candidate. Rank is derived from stardust: the handler resolves the highest
level whose `requiredStardust` threshold the candidate meets, then:

- no rank submitted → the earned rank is assigned
- a lower rank submitted → raised to the earned rank ("enhancing")
- a higher rank submitted → rejected with 400
- an unknown rank code → rejected with 400

Errors carry the field name as their target, so Fiori shows them on the
offending input rather than in a generic message strip.

Because the entity is draft-enabled, the handler is bound to `SAVE` rather
than `CREATE`: `SAVE` is the point at which the user commits the record.
Drafts intentionally accept incomplete data, which is why validation errors
surface on activation rather than while typing.

**`@After` (`srv.after('SAVE', ...)`)** — sends a welcome message to the new
spacefarer.

Failures are caught and logged, never rethrown. This is deliberate: an
undeliverable congratulation does not invalidate a valid application, and
the `after` handler runs inside the transaction, so an uncaught error would
roll back the whole creation.

Delivery is isolated in a single `sendEmail` method — the replaceable
boundary. Swapping the `console.log` for nodemailer or the SAP Alert
Notification service leaves the calling code untouched.

In production this would not run inside the transaction at all: CAP's
`cds.outboxed()` defers delivery until after commit and makes it retryable,
which is the correct shape for any outbound side effect.

## Fiori application

A single Fiori elements application (`app/spacefarers`) providing both the
List Report and the Object Page. `@odata.draft.enabled` on the service entity
gives the Object Page its edit flow; CAP generates the draft tables and
actions from that one annotation.

Pagination works through OData `$top`/`$skip`, which CAP translates to SQL
`LIMIT`/`OFFSET` — see the paging request in `tests.http`. The Fiori table
uses this automatically while scrolling.

Labels come from `@title` annotations on the model, so they appear in
`$metadata` as `Common.Label` and are available to any OData client, not just
this UI. Presentation-only annotations (`UI.LineItem`, `UI.SelectionFields`)
live in `app/spacefarers/annotations.cds`, separate from the semantic model.

## What I would do differently in production

- Outbox the welcome message instead of sending it inside the transaction.
- XSUAA instead of mocked users, with planet as a role attribute.
- Re-evaluate the `Integer` skill key (see Data model above).
- Localize labels through `i18n.properties`; the code lists already carry
  `localized` text via their `.texts.csv` files.
